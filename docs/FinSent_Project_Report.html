Abstract

Financial decision-making today is increasingly shaped by two fast-moving information streams: market data and textual news flow. While market prices provide measurable historical and real-time information, financial headlines provide qualitative context regarding catalysts, expectations, macro events, sector sentiment, and company-specific developments. In practical settings, the challenge is not only to read these sources independently, but to combine them in a structured way that helps users identify whether a stock currently exhibits bullish, bearish, or neutral short-term signals. This project addresses that problem through the design and implementation of FinSent, a prototype platform for integrating financial news analysis with short-term market context and presenting the result through an interactive dashboard.

The proposed system implements a modular pipeline that acquires financial news from provider-specific sources, normalizes articles into a common schema, performs article-level sentiment and impact analysis, retrieves current quote snapshots and recent OHLCV price bars, computes a composite signal using deterministic application logic, stores structured records in a local SQLite database, and presents the processed information through a Plotly Dash interface. The project also includes support utilities for symbol mapping, dataset import, data quality checks, cache-aware refresh behavior, and fallback modes that maintain system continuity even when some live provider inputs are unavailable.

A key focus of the work is on robustness rather than only nominal functionality. The implementation explicitly handles stale quote states, sparse news conditions, malformed model outputs, provider mismatch across US and Indian exchanges, and the need to distinguish between fully integrated Market + News operation and fallback modes such as Market-only or News-only. The project therefore does not present a black-box sentiment demo, but instead a structured analytics workflow where data quality, freshness, and explanation are visible to the end user. Functional correctness is validated through unit and runtime tests covering news persistence, market bar normalization, signal scoring, impact calculation, provider selection, and status messaging.

The final outcome is a working end-to-end prototype that demonstrates how modular financial analytics software can be built using standard software engineering practices, database-backed persistence, provider abstraction, and user-facing visualization. The project establishes a strong base for future work such as large-scale backtesting, portfolio features, alerting, stronger validation, and deployment beyond a single local environment.

Keywords: financial news analytics, sentiment analysis, stock market dashboard, short-term trading signal, SQLite, Plotly Dash, financial NLP, market data integration.

Chapter 1
Introduction

This chapter introduces the motivation and context of the FinSent project. It explains why short-term stock analytics cannot rely only on price charts or only on qualitative headlines, formulates the problem that the project addresses, defines the objectives and scope of the work, and summarizes the methodology adopted to design, implement, validate, and present the final prototype.

1.1 Background

Modern financial decision-making increasingly depends on the ability to interpret large and rapidly changing information streams. Traders, analysts, students, and researchers are exposed to price movement, order-flow proxies, macro events, analyst opinions, sector trends, and company-specific announcements in parallel. Looking at any one of these streams in isolation often produces incomplete understanding. A stock may show a temporary upward movement while underlying news remains weak; conversely, a strong product announcement may not immediately be reflected in the observed market structure if quote data are stale or if the event is still being priced in.

In practical environments, this creates a recurring need for systems that can gather multiple forms of financial information, normalize them into a common representation, and present them in a concise decision-oriented interface. The project reported here is motivated by exactly that need. Instead of building a pure text classifier or only a visualization dashboard, the project attempts to bridge the gap between qualitative market narrative and measurable price behavior. The result is FinSent, a local prototype designed to collect news, fetch market data, compute short-term signal interpretations, and present the result through an interactive dashboard.

The background of this work lies at the intersection of financial text analytics, market microstructure awareness, software engineering, and applied data systems. A realistic finance-related system cannot assume perfect data availability. News may be sparse, provider APIs may return incomplete responses, price bars may be missing for specific exchanges, and model outputs may occasionally be malformed or uncertain. Therefore, the background problem is not only “how to classify financial news,” but also “how to build a software system that remains informative when the data quality is mixed.” FinSent approaches the problem from that system-level perspective.

The project is also shaped by the changing role of interactive dashboards in engineering applications. Dashboards are no longer expected only to display static metrics. Users now expect them to encode data freshness, indicate fallback modes, present narrative explanations, compare entities, and help with actionable interpretation. In that sense, FinSent is not simply a reporting interface layered over stored data; it is a decision-support prototype that continuously balances analysis, data quality signaling, and usability.

Another important background factor is the availability of both seeded and live data. The project combines local CSV-based historical datasets with provider-based runtime sources. This combination allows the system to remain useful in different conditions. Historical datasets are helpful for initialization, experimentation, and baseline charting, while live sources provide freshness and make the dashboard meaningful as a near-real-time workspace. Together, they make the prototype closer to a realistic applied engineering project than a pure academic toy model.

1.2 Problem Statement

Investors and analysts often consume financial news and market prices separately. This separation causes several problems. First, text-heavy news feeds do not easily reveal whether an event is likely to matter in the short term. Second, raw price charts do not explain why a movement may be occurring or whether the current price context is supported by fresh relevant news. Third, when users manually combine both streams, the process becomes time-consuming, inconsistent, and difficult to scale across multiple stocks and exchanges.

The central problem addressed in this project is therefore the design of a software platform that can integrate financial news and market data, convert them into a structured analytics pipeline, and deliver an interpretable short-term signal to the user. The platform must work with heterogeneous inputs, support both US and Indian market symbols, persist the results in a database, and present the final outcome in a dashboard that is readable even when some live inputs are degraded.

The problem extends beyond data retrieval. It includes the need for symbol normalization, news deduplication, article-level analysis, aggregate view generation, composite scoring, explicit fallback states, and traceable explanations. A system that merely predicts “positive” or “negative” sentiment without exposing the freshness or reliability of the underlying inputs would not meet the practical needs of the project. Hence, the problem statement includes both analytical correctness and software robustness.

In concise form, the problem statement can be written as follows: to design and implement a modular financial analytics system that combines financial news and market data to generate and visualize short-term stock signals, while maintaining clear data provenance, quality indicators, and fallback behavior when complete live data are not available.

1.4 Scope of Project

1.4.1 Core System Scope

The core scope of the project covers data ingestion, analysis, persistence, and presentation. This includes provider-aware news acquisition, live or delayed market quote retrieval, OHLCV bar handling, article-level analysis, aggregate sentiment generation, composite signal scoring, data storage using SQLite, and dashboard visualization. It also includes seeded CSV imports for historical price support and company-universe bootstrapping.

The scope covers a prototype-level analytics workflow rather than a production-grade brokerage, order execution, or portfolio management platform. The system is designed to inform short-term reading of signals and not to automate trading. The application supports a curated but meaningful stock universe and demonstrates extensibility for additional symbols and sources.

1.4.2 Analytics and Intelligent Feature Scope

The analysis layer of the project focuses on headline interpretation, short-term impact estimation, aggregate sentiment synthesis, and deterministic signal scoring. This scope is intentionally narrower than full quantitative forecasting or deep historical alpha modeling. The project does not claim to produce guaranteed trading returns, optimize portfolios, or replace financial research. Instead, it presents a carefully engineered system for integrating textual and market context and making the output easier to interpret.

Likewise, the project does not include a custom-trained large transformer model or extensive model benchmarking over millions of labeled samples. The intelligent portion of the system is used as one component inside a broader application workflow. This limited but practical scope helps keep the work implementable within semester constraints while still making the project technically meaningful.

1.5 Methodology

The methodology adopted in this project follows an iterative system engineering approach. The work began with problem understanding and requirement identification, followed by the design of a layered architecture. The implementation then proceeded module by module: symbol handling, provider abstraction, article normalization, market data normalization, signal computation, persistence, and dashboard integration. Each module was refined based on runtime behavior rather than being frozen after first implementation.

A hybrid validation strategy was used. Instead of restricting the project to one final demo, multiple categories of testing were added. Pure analytical functions such as news-to-price alignment and daily summary generation were unit tested. Signal scoring logic was tested for deterministic outcomes under controlled inputs. Runtime-style tests were added for news persistence, provider selection, malformed analyzer responses, and India-specific price bar normalization. The methodology therefore emphasized not only building the system but also demonstrating that individual components behave correctly under expected and edge-case conditions.

Documentation and chapter planning were also treated as part of the methodology. Because the final report is expected to describe both conceptual and implementation aspects, the project was approached as a sequence of connected tasks: literature understanding, design formulation, implementation, verification, observation, improvement, and technical reporting. This report mirrors that methodology.

Chapter 2
Literature Survey

This chapter reviews prior work relevant to the proposed system. It examines financial text analytics, sentiment-based market interpretation, transformer-based language models, and practical decision-support systems that combine structured and unstructured data. The chapter concludes by identifying the research gap addressed by the project and presenting a comparative view of the reviewed literature.

2.1 Financial Text Analysis and Sentiment Modeling

Financial text analysis has been an active research area because price movement is strongly affected by narrative context. Loughran and McDonald [1] showed that generic sentiment dictionaries often perform poorly on financial text because domain-specific language can invert common-language polarity. Terms such as “liability” or “debt” may not always indicate negative outlook in standard finance communication, and words such as “volatile” can be descriptive rather than necessarily bearish. Their work is important because it established the need for finance-aware text interpretation rather than naïve application of general-purpose sentiment tools.

Tetlock [2] demonstrated that media tone carries measurable information for market behavior. His work showed that pessimistic language in financial news can influence market responses and can be linked to subsequent market activity. The contribution of this line of work lies in validating the practical relevance of textual signals for finance. It moves the discussion from pure linguistic classification to economically meaningful interpretation.

Later work extended sentiment modeling from dictionary methods to machine learning and deep learning. Financial news contains abbreviations, sector-specific jargon, earnings language, analyst vocabulary, and event-driven context that often require contextual interpretation. This motivated the use of supervised learning, embedding-based methods, and transformer architectures for domain-sensitive classification. From a project perspective, this literature supports the idea that headline sentiment is not a decorative feature but a valid signal dimension when handled carefully.

2.2 News-Driven Market Prediction Systems

Schumaker and Chen [3] explored the use of breaking financial news for market prediction and showed that structured extraction from news could improve predictive systems. Their work is especially relevant because it moves beyond pure document classification and asks whether news can be transformed into a market-useful signal. In a similar spirit, Bollen, Mao, and Zeng [4] investigated whether collective mood and social content have predictive value for market behavior. While social media is not the focus of the present project, the broader lesson is that textual information can carry market-relevant signal content when processed systematically.

Xing, Cambria, and Welsch [5] surveyed natural-language-based financial forecasting approaches and emphasized that financial forecasting from text is challenging because it requires connecting event semantics, sentiment intensity, timing, and price dynamics. Their analysis makes clear that success in this domain depends not just on language accuracy but on system design, temporal alignment, and interpretability. This is directly relevant to FinSent, where the goal is not to produce a standalone label but to connect article timing with price context and then expose the result to the user.

Several research efforts also highlight the importance of hybrid systems that combine structured price data with text-derived features. In many cases, text alone provides direction but lacks market calibration, whereas price alone provides reaction but lacks explanation. This literature supports the design decision in FinSent to generate a composite signal using both news-related analysis and market context, rather than relying exclusively on one modality.

2.3 NLP, Transformer, and Domain-Adapted Language Models

Devlin et al. [6] introduced BERT, which significantly improved contextual language understanding by pre-training deep bidirectional transformer representations. BERT’s impact extends to many domains, including finance, where contextual understanding is important for interpreting short headlines and limited textual summaries. Araci [7] proposed FinBERT as a domain-adapted financial language model and showed that financial sentiment tasks benefit from specialized pretraining and fine-tuning. Even though the current runtime path in FinSent relies on a different analysis architecture, the literature around FinBERT remains important because it demonstrates why finance-specific modeling assumptions matter.

More recent systems increasingly rely on instruction-following large language models for structured extraction, summarization, and reasoning over limited context windows. These systems can return relevance, sentiment, confidence, and short rationale in a structured JSON-like form, making them attractive for prototype-level financial analytics pipelines. However, they also introduce concerns around cost, rate limits, malformed outputs, and reliability. This duality is reflected in the design of FinSent, where analyzer output is not accepted blindly but is normalized, capped, and combined with deterministic application logic.

The literature therefore suggests an important balance. Domain-adapted NLP models can improve semantic understanding, but robust systems still need validation rules, fallback behavior, and explicit scoring logic. FinSent adopts that balance by separating article interpretation from final signal computation.

2.4 Dashboard-Oriented Financial Analytics Systems

Many finance tools present charts, tables, and alerts, but not all of them make data quality visible. Academic and industrial dashboard systems increasingly focus on explainability, provenance, and workflow support in addition to metric display. A good analytics dashboard should help the user answer questions such as: Is the displayed signal based on current quotes? Are the headlines relevant? Is the system operating under fallback conditions? What is the most likely catalyst behind the signal?

The design of FinSent aligns more closely with this interactive analytics philosophy than with a static reporting interface. The dashboard is expected to serve as a workspace where charts, badges, status pills, tables, and signal notes all work together. This design orientation is strongly influenced by practical dashboard literature and official framework documentation [12], where component-based UI composition, callback-driven state updates, and modular view-model design are emphasized.

From a literature standpoint, dashboard systems matter because they determine whether advanced analysis remains usable. A highly accurate model hidden behind a poor interface may have limited decision-support value. By contrast, an interpretable dashboard with clear explanation and freshness cues can be more useful for real users even if the backend analytics remain intentionally conservative.

2.5 Summary and Research Gap

The reviewed literature confirms five important points. First, financial text requires domain-aware interpretation. Second, textual sentiment can influence market behavior and should not be ignored in short-term analysis. Third, effective systems must connect textual outputs with timing and market context. Fourth, transformer and LLM-style systems improve expressiveness but require careful integration and validation. Fifth, user-facing dashboards are most useful when they communicate not only the signal but also the assumptions and quality of the supporting data.

Despite this progress, a gap remains for academic prototype systems that integrate these ideas into a modular, inspectable, and testable software stack. Many papers focus on model accuracy, while many dashboards focus on visualization without transparent runtime data quality indicators. The gap addressed by FinSent is the construction of a practical finance analytics prototype that combines provider abstraction, structured persistence, runtime fallback behavior, short-term signal synthesis, and interactive visualization within one cohesive system.

Chapter 3
Project Design and System Architecture

This chapter describes the design of the proposed system. It explains the system overview, requirements, software modules, architecture, workflow, datasets, database design, and technology stack. The chapter establishes how the project translates literature and requirements into a practical and modular implementation architecture.

3.1 System Overview

FinSent is a modular software platform for stock-centric short-term analytics. The system accepts a selected symbol as its primary input, resolves that symbol into provider-specific and exchange-specific forms, acquires relevant news and market data, analyzes headlines for short-term sentiment and impact, computes a composite market-news signal, stores the resulting state in a local database, and serves the output through an interactive dashboard. The dashboard presents summary, stock detail, news impact, comparison, and alert-style views over the same common backend state.

The system is designed so that each stage can be independently improved without rewriting the entire stack. For example, a new market provider can be introduced without changing the dashboard logic, and a new analyzer can be added without restructuring the persistence layer. This modularity is important because financial data systems evolve quickly and often need provider substitution due to cost, reliability, or coverage changes.

The system also distinguishes between raw input, normalized data, persisted data, and derived analytics. This separation allows each layer to have a clear responsibility. Raw provider responses are converted into normalized objects and data frames. Persisted data act as a reusable state store. Derived analytics such as event alignment and comparison metrics are computed closer to the presentation layer. This design is beneficial for debugging, testability, and reportability.

3.4 System Architecture

The overall architecture of FinSent is layered. At the bottom are raw data sources: provider APIs and local datasets. Above them is a normalization layer that converts heterogeneous inputs into common structures such as normalized news articles, quote snapshots, and OHLCV data frames. The intelligence layer then combines article analysis and market context to produce aggregate views and composite signals. A persistence layer stores all significant outputs. Finally, the view-model and dashboard layers transform stored and derived data into charts, cards, tables, and status indicators.

One strength of this architecture is that it distinguishes between runtime intelligence generation and dashboard-time analytics assembly. The intelligence service is responsible for obtaining and persisting fresh data. The dashboard view model then loads the necessary stored data and builds dashboard state objects, including event frames and comparison metrics. This avoids recomputing expensive provider calls during every simple UI interaction.

Another architectural strength is explicit fallback modeling. If market data exist but relevant news are unavailable, the architecture still yields a valid mode rather than failing silently. If quote quality is stale, the dashboard can still show the information but label it properly. This emphasis on operational truthfulness is one of the defining design decisions of the project.

3.5 Workflow and Data Movement

The runtime workflow starts when the user selects a ticker or loads an analysis page. The dashboard checks whether data need refresh. If refresh is required, the intelligence service resolves the symbol and invokes the appropriate market and news providers. Market providers return current quote snapshots and recent price bars. News providers return normalized article objects, which are deduplicated before analysis. Each article is then checked against cached analytical results. If no cached analysis exists, it is analyzed and persisted.

Once all article-level outputs are available, an aggregate analytical view is generated and then passed with market context into the composite signal engine. The resulting quote snapshot, price history, article data, and signal snapshot are written to the database. Later, when the dashboard builds its state, it loads the relevant persisted data, filters them by selected horizon or date window, aligns news to price movement, and derives view-specific metrics such as mean sentiment, impact summary, sector comparisons, and final note text.

This workflow supports both reproducibility and responsiveness. Because intermediate outputs are persisted, the dashboard can load quickly and does not depend entirely on re-fetching data every time the user navigates. At the same time, refresh logic ensures that stale data are not presented as if they were fresh.

3.8 Core Algorithms and Logical Design

Although FinSent is presented as a dashboard platform, its usefulness depends on a sequence of interconnected software algorithms. The first algorithmic layer is symbol resolution. This logic ensures that a user-provided identifier is mapped to a canonical stock record before any external provider is called. Such resolution is essential when the same company appears in different exchanges or when providers require exchange-prefixed, suffixed, or internally normalized identifiers.

The second major algorithmic layer is article normalization and deduplication. Incoming news articles may differ in provider structure, but the system converts them into a standard structure containing title, source, published time, URL, and provider metadata. Deduplication is based on a hash generated from article title and URL. The practical reason for this step is to prevent duplicate news stories from exaggerating sentiment or artificially increasing article counts.

The third algorithmic layer is article analysis. For each article, the system estimates whether the article is relevant to the stock, whether it indicates bullish, bearish, or neutral short-term sentiment, how strong the likely impact is, what time horizon is implied, and what catalyst category best describes the event. The system is designed so that this layer can be backed by structured analyzer output or by heuristic fallback logic. This makes the project both flexible and stable.

The fourth algorithmic layer is aggregate interpretation. Multiple article-level results are combined into an overall view by considering relevance, confidence, and impact. Instead of treating each article equally, the system gives more weight to stronger and more confident signals. This produces an aggregate sentiment and confidence level that better represents the overall news situation around a stock.

The fifth algorithmic layer is composite scoring. This is one of the most important logic blocks in the project. The composite signal engine does not blindly trust text analysis, and it does not blindly trust market data. Instead, it synthesizes both by combining a news-derived score with a market-derived component while also applying penalties related to liquidity spread and data freshness. The outcome is a final composite score, a categorical label, and a mode indicating whether the system is operating under full or fallback conditions.

The sixth layer is analytical alignment between news and prices. The market impact module aligns each article timestamp with the nearest available entry price and then finds a future price for a specified return window. From these two points it derives forward return. This allows the project to move beyond sentiment display and toward measured event-price linkage. At the next level, a daily summary function aggregates event counts, mean sentiment, mean forward return, and correlation estimates over grouped events.

From a logical-design standpoint, the project follows a “normalize first, score later” principle. That is, raw provider data are not used directly for user-facing decisions. Instead, they are normalized, validated, deduplicated, and persisted before higher-level metrics are derived. This improves repeatability and reduces hidden dependency on provider-specific structures. The project also follows a “signal with context” principle: the user is shown not only what the signal is, but also whether it came from integrated data, market-only fallback, or other degraded states.

3.9 Ethical, Academic, and Practical Considerations

Since the project concerns market-related analytics, it is important to state that the system is designed as a decision-support and educational prototype, not as an automated financial-advice platform. The output of the system should not be interpreted as guaranteed investment guidance. This distinction is important both academically and practically. In an academic setting, it shows clear awareness of scope. In a practical setting, it reminds users that analytics systems can assist judgment but should not replace it entirely.

Another important consideration is data integrity. The project includes multiple sources, multiple transformations, and different freshness levels. Therefore, representing quality, fallback state, and provenance is part of responsible system design. A prototype that hides these uncertainties would be easier to present superficially, but less trustworthy as an engineering artifact. FinSent instead exposes enough system state so that the user can see the basis on which the displayed result was produced.

From an academic point of view, the work also needs to remain honest about its contribution. The project does not claim to have invented a new state-of-the-art financial prediction model. Its contribution lies in the structured engineering of a modular analytics workflow, the integration of textual and price-based data, the persistence design, the dashboard implementation, and the validation approach used to show reliable behavior. This framing is academically sound and aligns the report with the actual work performed.

Chapter 4
Implementation and Experimentation

This chapter presents the practical realization of the system. It describes the development environment, core implementation modules, runtime behavior, testing strategy, functional validation, observed results, and design modifications made after analysis. 4.1 Development Environment and Setup

The project was implemented in Python using a virtual environment for dependency isolation. The environment includes Dash for the dashboard, SQLAlchemy for persistence, Pandas and NumPy for data handling, Requests for provider access, and additional application-specific utilities for symbol management and runtime orchestration. The development process followed an iterative loop of coding, local execution, observation, patching, and test-based verification.

The repository is organized so that the application layer, provider layer, database layer, dashboard layer, and test layer remain separated. This made it easier to reason about errors. For example, when price bars were not appearing correctly for specific markets, the issue could be traced either to the market provider normalization path or to view-model filtering logic rather than being lost inside a monolithic script.

The implementation also had to accommodate the reality that the dashboard should be runnable from a project-local interpreter rather than assuming globally installed packages. This is important for reproducibility and for academic demonstration, because many runtime issues in prototypes are caused not by logic errors but by environment mismatches. The final project therefore emphasizes a consistent local execution path through the project virtual environment.

4.2 Implementation Details

4.2.1 Symbol Resolution and Provider Mapping

A key design challenge in financial software is that the same real-world stock can be represented differently for different exchanges and providers. The project solves this using a symbol registry layer that stores an internal record for each supported symbol. This record includes ticker, display name, exchange, provider symbol, sector, and optional provider-specific identifiers. This normalization allows the rest of the system to work with consistent symbol semantics even if the raw provider strings differ.

This implementation decision is especially useful for supporting both US and Indian symbols. A user-facing symbol may be entered as a raw ticker, an exchange-prefixed symbol, or a market-suffixed name. The registry resolves these forms into a canonical record before the provider layer is invoked. This reduced downstream branching and kept provider code cleaner.

4.2.2 News Acquisition and Normalization

The news provider layer abstracts multiple acquisition strategies. Different provider classes fetch and normalize articles into a common `NormalizedNewsArticle` structure. This structure includes title, source, URL, published timestamp, provider, dedupe hash, and relevance score. By using a normalized structure, the rest of the system is decoupled from provider-specific response shapes.

An important implementation detail is the use of deduplication. Financial stories are often syndicated, repeated, or refreshed. If duplicate articles are processed repeatedly, the final signal may be biased. Therefore, the intelligence service sorts incoming articles, removes duplicates by hash, and then checks whether analytical results for the article are already cached in the repository. This improves both efficiency and stability.

4.2.3 Market Data Acquisition

The market provider layer retrieves current quote snapshots and historical price bars. The code distinguishes between immediate quote-like data and bar-based history. Quote snapshots are useful for current price display, freshness estimation, and spread-based logic. Price bars are useful for charts, price change summaries, and event alignment. Keeping these two forms separate is important because they may have different refresh rates, quality states, and provider support.

The normalization of price bars into the standard OHLCV structure is one of the practical achievements of the implementation. Different providers and imported datasets expose market history differently. The project converts them into a consistent format so that analytical functions can remain provider-agnostic. This is validated through runtime tests.

4.2.4 Article Analysis and Aggregate Interpretation

For each article, the analyzer layer produces structured fields such as relevance, sentiment, confidence, impact strength, time horizon, catalyst tag, and short reason. The aggregate layer then combines all article-level results into an overall sentiment view, overall confidence, action bias, and summary reason. The project architecture intentionally separates article-level interpretation from final signal scoring because these are conceptually different tasks.

An important practical feature is fallback analysis. If structured analyzer output is malformed or unavailable, the system falls back to heuristic article analysis. This makes the implementation more resilient and prevents a single analyzer issue from making the dashboard unusable. The test suite explicitly verifies safe handling of malformed numeric analyzer outputs.

4.2.5 Composite Signal Scoring

The composite signal engine combines article-derived information with quote-related context to produce a final score, label, confidence, and operating mode. This engine is deterministic application logic. That means the final signal is not simply copied from one model output. Instead, it is computed by weighting recency, confidence, impact strength, market freshness, and liquidity-related penalties. This design was chosen because it offers better explainability and greater control over behavior under partial data conditions.

Another benefit of this approach is that operating modes become explicit. When both market and news context are available, the mode is `Market + News`. If only market data are present, the system enters `Market-only fallback`. If only news are present, it enters `News-only fallback`. This clarity is valuable in an academic prototype because it makes the system behavior easier to interpret and defend.

4.2.6 Database Persistence

The persistence layer stores all meaningful outputs from the intelligence refresh cycle. News records preserve not only article text and provider metadata but also analysis-specific fields. Price history is stored as structured OHLCV records. Quote snapshots and signal snapshots capture the latest market and analytical state. This persistent model allows the dashboard to reload quickly and makes the application state inspectable for debugging and testing.

A practical advantage of the persistence design is that it supports partial recomputation. If a quote is already stored but new news arrive, not everything has to be rebuilt from scratch conceptually. The repositories create a stable interface between runtime acquisition and user-facing views.

4.2.7 Dashboard Implementation

The dashboard is built using Plotly Dash with multiple pages. The summary page presents top-level status, metrics, a primary chart, and signal notes. The stock detail page provides deeper charting and stock-specific statistics. Additional pages support comparison, news-impact inspection, and alert-style watchlist logic. The view-model layer computes dashboard state so that pages remain relatively declarative.

The dashboard design evolved significantly during the project. Earlier views relied too heavily on dense explanatory text and charts that were not always meaningful when data were sparse. Through iteration, the dashboard was refined toward clearer cards, status pills, more honest fallback notes, and simplified visuals such as fixed recent-price bars for summary views. This change demonstrates that implementation in analytics systems includes UX calibration, not only backend coding.

4.2.8 Database Schema and Repository Realization

On the implementation side, the database schema is realized through SQLAlchemy entity definitions. Each database entity captures a clear slice of application state. The `news_articles` table stores article metadata and analysis-related fields. The `price_bars` table stores the normalized OHLCV history required for charts and event alignment. The `quote_snapshots` table records live or delayed quote context, while the `signal_snapshots` table stores the final computed state of the application’s short-term signal layer.

The repository layer was implemented to hide raw database operations from the rest of the application. This improves readability and keeps data access logic centralized. Repositories also allow targeted testing of persistence behavior, making it easier to verify that the stored and retrieved data maintain the correct structure across refresh cycles.

4.2.9 View-Model and Callback Orchestration

A notable engineering part of the project is the dashboard view-model layer. Rather than placing all transformation logic directly inside UI callbacks, the project computes a `DashboardState` that bundles news, prices, event summaries, comparison frames, snapshot maps, and data-quality metadata. This pattern reduces duplication across pages and improves maintainability.

The callback architecture also demonstrates event-driven software design. User interactions such as selecting a ticker, changing the time window, or refreshing live data trigger state updates. These updates then propagate to the visible components. This design keeps the interface responsive and makes the code path easier to reason about during debugging.

4.4 Results and Discussion

The project resulted in a working prototype capable of loading supported symbols, retrieving or reusing data, computing structured short-term signal information, and presenting it through multiple dashboard views. The implementation demonstrates that a finance analytics system can be built in a modular way where providers, repositories, analytics functions, and UI state assembly remain separable and testable.

From a functional perspective, the system achieved the intended workflow: news articles are fetched and normalized, quote snapshots and recent bars are obtained where supported, article-level signals are computed, aggregate outputs are derived, data are persisted, and the dashboard uses those outputs for user-facing metrics and charts. This confirms that the project meets its main system-integration objective.

From a robustness perspective, one of the most meaningful outcomes is the introduction of explicit fallback modes. Instead of assuming ideal conditions, the system differentiates between complete and partial input states. This result is important because it improves trustworthiness. A user can understand whether a displayed signal is based on both market and news data or only one source.

From a UI perspective, results showed that overly abstract or sparse sentiment charts can be less useful than simpler and more literal views. This led to modifications in chart presentation and summary wording. The broader lesson is that a successful analytics system depends not only on algorithmic processing but also on representation choices that match user expectations.

4.6 Design Modifications Based on Observed Results

The system was modified several times after early runs and testing. First, the project moved away from a narrow legacy sentiment path toward a broader runtime pipeline built around provider normalization, article analysis, and deterministic composite scoring. This increased control and made the behavior easier to test.

Second, the system added stronger status indicators. Rather than quietly failing when bars or fresh articles were absent, it began exposing price source, bars status, freshness age, news tier, and operating mode. This improved interpretability and reduced ambiguity.

Third, chart design was simplified. Initial chart outputs were sometimes technically valid but not practically readable. This led to replacing visually confusing charts in summary contexts with simpler daily-bar presentations. That change was not only aesthetic; it was a usability improvement based on analysis of how the dashboard was actually being interpreted.

Fourth, repository and runtime tests were expanded. As more provider and fallback paths were introduced, the need for regression prevention increased. Adding tests around persistence, malformed outputs, and India-specific market-bar normalization reduced the risk of silent breakage.

Chapter 5
Conclusion, Limitations, and Future Work

This chapter presents the final conclusions drawn from the work, identifies the main limitations of the current prototype, and outlines the future development opportunities that can extend the project into a more mature and scalable financial analytics platform.

5.1 Conclusion

The FinSent project successfully demonstrates the design and implementation of a modular financial analytics prototype that combines qualitative news interpretation with quantitative market context. The work began with the observation that price charts alone do not explain market behavior and that textual news alone does not provide sufficient market calibration. By integrating both streams through a structured pipeline, the project delivers a more interpretable short-term stock analysis experience.

The major contribution of the project is not a single algorithm in isolation, but the engineering of an end-to-end system. This includes symbol resolution, news normalization, market-data normalization, article-level analysis, aggregate reasoning, deterministic composite signal scoring, persistent storage, and dashboard presentation. The work therefore demonstrates strong system-integration value and reflects practical software engineering concerns such as provider abstraction, fallback behavior, testing, and UI readability.

Another important conclusion is that truthful system behavior is as important as analytical sophistication. In finance-related software, incomplete or stale data are common. A project that hides these conditions can mislead users. FinSent addresses this by showing operating mode, freshness, quote quality, and other status cues. This makes the prototype more reliable as a decision-support tool.

Finally, the testing results show that the project is not only demonstrable but also verifiable. Key analytical functions and runtime flows were validated through targeted test cases. This adds credibility to the implementation and makes the project stronger as an academic submission.

  • The project achieved its primary objective of integrating market and news signals into a single dashboard-driven workflow.
  • The modular design improved maintainability and allowed clear separation of concerns.
  • Runtime fallback behavior significantly improved robustness and usability.
  • The system provides a practical prototype foundation for future finance-oriented analytics extensions.

5.2 Limitations

Although the system is functional, it has clear limitations. The first limitation is dependence on external data providers. API availability, latency, quotas, or format changes can affect system behavior. The second limitation is that the current project emphasizes functional validation rather than deep historical performance benchmarking. While the prototype computes useful signals, it does not yet include a large-scale backtesting framework to quantify predictive performance over long horizons.

A third limitation is that the supported symbol universe is curated rather than exhaustive. This makes the project easier to manage academically but limits universal market coverage. A fourth limitation is that the database layer uses SQLite, which is ideal for local prototyping but not for multi-user or production-scale deployment. A fifth limitation is that analyzer quality depends on upstream output stability. While the project includes fallbacks and sanitization, model behavior can still vary in ways that require careful interpretation.

A final limitation is that the dashboard is optimized for clarity rather than institutional-grade analytical depth. Features such as portfolio tracking, alert subscriptions, backtest reports, and user-role-based collaboration are not yet implemented. Therefore, the system should be viewed as an applied academic prototype and not a complete commercial financial platform.

5.3 Future Scope

  • Add large-scale historical backtesting to evaluate signal quality across different sectors, horizons, and market conditions.
  • Expand the supported symbol universe and add richer exchange coverage.
  • Introduce a stronger persistence backend such as PostgreSQL for larger deployments.
  • Support asynchronous background refresh jobs and more advanced caching strategies.
  • Improve explainability by linking individual articles more explicitly to final signal contributions.
  • Add alerting, watchlists, and portfolio-level tracking for practical user workflows.
  • Introduce model comparison and calibration layers to evaluate multiple analyzer strategies.
  • Provide exportable reports and scheduled daily summaries for operational usage.
  • Package the project for containerized deployment and remote multi-user access.

Overall Closing Remark: FinSent demonstrates that a thoughtfully engineered academic prototype can go beyond a simple classroom demo and evolve into a realistic decision-support system. Even in its current form, it shows how financial news, market data, database persistence, and interactive visualization can be combined into a coherent and extensible analytics platform.

Appendix D
Core Algorithm Descriptions

This appendix summarizes the logical flow of the most important software algorithms used in the project in plain engineering language.

D.1 Symbol Resolution Algorithm

Accept raw user ticker input, normalize case and suffix style, attempt direct provider-symbol match, attempt exchange-suffixed match, then fall back to exchange-specific ticker lookup. If a valid symbol record is found, use it as the canonical runtime identity for subsequent processing.

D.2 News Refresh Algorithm

Fetch recent articles from the configured news provider, normalize each article to the common project schema, compute a dedupe hash, remove duplicates by recency order, and then pass each surviving article into the article-analysis stage. Reuse cached analysis if already stored.

D.3 Composite Signal Algorithm

For each analyzed article, compute a recency-weighted contribution using article confidence and impact strength. Normalize total news contribution, blend it with a market component, apply liquidity and freshness penalties where appropriate, cap the final result to a bounded range, and then derive a label and operating mode.

D.4 Event Alignment Algorithm

For each article timestamp, find the nearest valid market entry price at or before publication time, then find a future price at the desired return window. Compute the forward return using the entry and future close values. Aggregate these event-level results by day to obtain mean sentiment and mean forward return summaries.

D.5 Dashboard State Construction Algorithm

Load persisted datasets for the selected ticker and comparison symbols, filter them to the active horizon or date window, derive event and summary frames, assemble metric cards, chart inputs, and explanation lines, and return one structured state object that each dashboard page can consume.
